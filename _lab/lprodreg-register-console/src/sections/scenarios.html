Chapter 4

The three example scenarios

One example project, three projected PLCs, each demonstrating a different shape of application — from the simplest possible register to full conveyor tracking to the purely stationary mode.

A single conveyor belt with a light switch. Products spawn, get detected, are tracked along the register while the belt runs, and are deleted once they reach the end — the smallest possible register application, and the one to read first.

LProdReg_Scenario_11 conveyor1 light switchno actuator

Line & principle of operation

The light switch trigger is simulated as a rising edge every 50 mm of belt travel: a product is inserted every 50 mm, each rotated 60° and offset 20 mm in Y from the last, cycling every 6 products. An externally called FO‑Sink lets the operator manually delete by product ID, source conveyor ID, name, or a characteristic (e.g. colour = blue).

  4. 4Monitor products in DB LProdReg_ProductDataBase; optionally trigger the FO‑Sink via Controls.Trigger_Sink after setting a deletionBy… input.

Three conveyors, a camera, two light switches, and two delta pickers — the fullest example, and the one that demonstrates conveyor tracking through the example FB TrackConveyor.

LProdReg_Scenario_23 conveyors1 camera + 2 light switches2 actuators · FB TrackConveyor

Line & principle of operation

One product conveyor (camera detects blue/red products), two container conveyors (light switches detect boxes = group 1, then pallets = group 2). Both conveyor prioritisations are set to mode 1 (highest X). Picker 1 uses a user‑defined priority (…_CASE_2) so it only ever picks blue products into the 4‑pocket boxes; picker 2 has no such filter and moves any full box onto a pallet. Both pickers are driven through the example FB TrackConveyor (see 7.2), called in OB132 TrackConv_Call, which also does the path planning via MC_MovePath from LKinCtrl.

Structure — OBs

Main (1)Axis funcs Belt_1–3; output‑cam trigger logic for both light switches; TON to simulate camera response; MC_MoveVelocity ×3; RegisterManager; Hmi_Main
TrackConv_Call (132)TrackConv ×2, LKinCtrl_MC_GroupReset ×2

Running it — watch table

  1. 1Enable both TrackConv instances — kinematics enable, reset, home and move to base position; status 16#7002 on success.
  2. 2Enable, reset, home Belt_1–3.
  3. 3Enable the RegisterManager — status 16#7003.
  4. 4Execute all three belts — sensor simulation starts; velocity auto‑overrides down once the first object enters actuator 1's zone.
  5. 5Monitor the database, or the included HMI, plus each actuator's pick/place interface.
  6. 6(optional) Open the kinematic trace to watch synchronising and path motion.
NoteIf allowPickInExitArea/allowPlaceInExitArea is on and the extension zone is too short, TrackConv moves to a “dump position” and auto‑triggers deletion of the falsely picked object via deleteProduct.

One static storage, three processing stations and two sources — the station‑based mode, entirely without conveyor tracking or an actuator. Products and containers are shifted between stations by hand‑triggered requests, and characteristics update as they move.

LProdReg_Scenario_31 static storage3 stations2 sources · station‑based mode

Line & operating modes

FO‑SourceStation and FO‑Station cannot be configured through the RegisterManager, so they're always called externally — the manager's own configuration here holds just the one static‑storage conveyor.

Station 1Products: shift to next station (mode 1) · Containers: —
Station 2Products: shift to next station (mode 1) · Containers: shift to next station (mode 1)
Station 3Products: place in container pocket (mode 3) · Containers: place on conveyor (mode 2)

Structure — Main OB

BlocksLProdReg_RegisterManager (1×), LProdReg_FoSourceStation (2×), LProdReg_FoStation (3×)

Running it — watch table

  1. 1Enable every flow object then the core FB, in that order — status 16#7003.
  2. 2Trigger product creation at station 1 (ID 3) and container creation at station 2 (ID 4); max 5 per station.
  3. 3Watch productData.productAvailable; shift station 1→2, then 2→3.
  4. 4Watch containerData.containerAvailable; shift station 2→3.
  5. 5At station 3, place products into container pockets 1–3 by placePocketNumber; an occupied pocket warns rather than errors.
  6. 6Once the container is full, place it onto the static storage — it then lives in the conveyor storage area, since a static storage is an FO of type Conveyor.
  7. 7(optional) Use the FO‑Station delete functions — first product, first container, or everything in a station.
